\# Gravity Desk Buddy (GDB) — User Identity Model



\## Purpose



This document defines the minimum GDB user identity model for the MVP and records future Buddy identity considerations.



> \*\*Core principle:\*\* Identity should stay stable even while the user, their progress, and their Buddy evolve.



\## Identity Layers



```text

Internal identity

→ user\_id



Public account identity

→ username



Human-facing identity

→ display\_name



Companion identity

→ Buddy identity

```



These layers serve different purposes and should not be treated as interchangeable.



\## Internal User Identity



\### `user\_id`



`user\_id` is the permanent internal identity anchor for a GDB user.



It should:

\- be generated by the system,

\- remain stable for the life of the account,

\- not change when the username or display name changes,

\- not change when streaks, Orbits, journeys, or other product state changes,

\- and be used by other tables to identify ownership.



Example:



```text

user\_id = 7

```



This lets GDB say:



```text

This focus session belongs to user\_id 7.

This journal entry belongs to user\_id 7.

This Buddy belongs to user\_id 7.

```



\## Username



The username is the user’s unique public handle.



Example:



```text

@JamesIsaac

```



\### Rules



\- Every username must be unique across GDB.

\- Uniqueness should be case-insensitive.

\- If `@JamesIsaac` exists, capitalization variants such as `@jamesisaac` or `@JAMESISAAC` should also be unavailable.

\- GDB should not automatically append random numeric suffixes.

\- If a username is taken, the user chooses another variation.

\- Username changes should be infrequent.

\- Current product direction: approximately one username change every 6 months.



> \*\*Design principle:\*\* GDB usernames should feel persistent and unique without forcing users into permanent presentation forever.



\## Display Name



The display name is the flexible human-facing name shown on the profile.



Example:



```text

James Isaac

```



Rules:

\- required at signup,

\- does not need to be unique,

\- can change more freely than the username,

\- changing it does not create a new GDB user.



Example:



```text

James Isaac

@JamesIsaac

```



and another user could still be:



```text

James Isaac

@JamesBuilds

```



\## Email



Email is private account data.



For the MVP:

\- it is used for account/authentication purposes,

\- it is not displayed publicly,

\- it is not part of the visible profile,

\- and it is not used as the user’s public identity.



Future professional-networking or contact options can be considered later.



\## Authentication Identity



Conceptually:



```text

user signs in

→ auth system verifies identity

→ backend maps that identity to one GDB user

→ backend uses that user’s user\_id

```



The backend should not trust the frontend to declare which `user\_id` the request belongs to.



Possible implementations later:



```text

user\_id

email

password\_hash

```



or, with an external provider:



```text

user\_id

email

auth\_provider\_id

```



The final authentication implementation is a later engineering decision.



\## Profile Picture



Profile picture should be optional.



For the MVP:

\- not required at signup,

\- can be added later,

\- eventually stored as an image reference/URL rather than the image itself inside the normal user row.



\## Identity vs Product State



Identity answers:



> \*\*Who is this user?\*\*

> \*\*What is happening to this user inside GDB?\*\*

\## Buddy Identity Model



The Buddy should have its own identity rather than being only a text label on the user.



Conceptually:



```text

User

→ user\_id

→ username

→ display\_name



Buddy

→ buddy\_id

→ buddy\_name

→ possible future buddy\_handle

```



\### `buddy\_id`



`buddy\_id` should be the Buddy’s permanent internal identity anchor.



It remains stable even if the Buddy’s name, appearance, personality, or progression changes.



\### `buddy\_name`



The user should name their own Buddy during onboarding after account creation.



Example:



```text

Nova

```



\### Future Buddy Handle



Long-term, a Buddy may also need a unique public identity for Orbit and Convergence systems.



Example:



```text

Buddy

Nova

@NovaVoyager

```



Whether the visible Buddy name itself must be globally unique remains open.



Possible approaches:



\### Option A — Globally Unique Buddy Name



```text

Nova

```



can only be claimed once across GDB.



\### Option B — Flexible Buddy Name + Unique Buddy Handle



```text

Buddy name

Nova



Buddy handle

@NovaVoyager

```



This preserves emotional naming freedom while allowing unique public Buddy identity later.



GDB should not lock this decision during the MVP.

\## MVP Scope



\### Included in the identity foundation



\- permanent `user\_id`

\- unique username

\- required display name

\- private email

\- authentication mapping to the GDB user

\- support for user-owned data

\- Buddy identity anchor planned structurally



\### Explicitly not part of the MVP



\- Orbits

\- social/community systems

\- direct messaging/chat

\- public email/contact system

\- payments/premium identity

\- Orbit-based professional networking

\- advanced Buddy social identity

\- Convergence

\- global Buddy-handle system

\- public Buddy-network interaction



\## Orbits and Convergence



Orbits are not part of the MVP.



Convergence is a future V3 concept and should not be implemented now.



However, the current identity model should avoid blocking those systems later.



> \*\*Design stable identity anchors now. Delay social identity rules until the product reaches the stage that actually needs them.\*\*



That means `user\_id` and eventually `buddy\_id` can exist before any Orbit, Buddy-handle, social, or Convergence layer is implemented.



\## Open Product Decisions



1\. Should Buddy names themselves be globally unique?

2\. Should Buddies eventually receive separate unique public handles?

3\. Should username history be visible, private, or not publicly exposed?

4\. Should the 6-month username-change interval remain the final rule?

5\. How much real-name information should a future professional GDB profile expose?

6\. What image-storage system should be used for profile pictures?

7\. Which authentication provider or credential system should GDB use?

8\. How should future Orbit / Convergence identity build on the base account model?



\## Core Design Principles



> \*\*Identity stays stable while progress evolves.\*\*



> \*\*A user’s public presentation can change without creating a new user.\*\*



> \*\*The username is unique; the display name is flexible.\*\*



> \*\*Email is private by default.\*\*



> \*\*The frontend should not be trusted to declare the user’s identity.\*\*



> \*\*The Buddy is owned by the user, but the Buddy is not the user.\*\*



> \*\*User identity and Buddy identity should both have permanent internal anchors.\*\*



> \*\*Build the identity foundation now; defer Orbit and Convergence social rules until later.\*\*
